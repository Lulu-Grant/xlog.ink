# 修改方案：内联动作标记协议（会话模型兼任路由）

> 2026-06-11 · 基于 V2 现有代码的增量修改方案
> 关联文档：[V2-DESIGN.md](V2-DESIGN.md)（总体设计）
> 本方案落地后，本文件第六部分的决策记录应同步合并进 V2-DESIGN.md 第十二部分。

---

## 一、背景与动机

### 当前实现的问题

V2 现有代码中，"什么时候浮现什么 UI" 由两套脆弱机制决定：

1. **上传卡**：前端用关键词正则猜 AI 回复内容（`js/ai-app.js` 的 `maybeShowUploadCard`，匹配 "上传|图片|照片|..."）。gemma 换个措辞（"配图""素材"）就失灵，用户将无法上传图片。
2. **生成卡**：后端检测回复末尾的 `[READY]` 标记（`api/chat.php`），机制正确但是孤例，没有泛化；且前端逐 delta 剥离 `[READY]` 时存在拆包闪烁（`[REA` + `DY]` 分两个 chunk 到达时，中间态会短暂显示）。

### 曾考虑并否决的方案：独立前置路由模型

设想：每轮用户输入先经过一个小模型分类（继续问答 / 弹上传 / 触发生成），再分发。
**否决理由**：

- 延迟叠加：路由模型必须在对话模型之前完成，每轮 TTFB 翻倍；
- 成本倒挂：绝大多数轮次是"继续收集信息"，路由模型每轮都跑，但几乎不产生分流收益；
- 判断权错位：上传卡该出现的时机，就是 AI 说出"有图要上传吗"的那一刻——这个判断天然属于正在生成这句话的对话模型，让一个不说话的模型去预测说话的模型，更慢且更不准。

### 采纳的方案

**会话模型兼任路由器**：模型在自然回复的末尾附带内联动作标记，一次调用同时完成"问答 + 路由"。这是轻量版 tool-calling——标准 tool-calling 要求模型输出结构化 JSON（gemma 量级不可靠），本方案只要求模型在固定几个标记词中选择，约束极强，小模型可以胜任。

## 二、两层路由模型（架构定义）

| 层 | 判断者 | 触发条件 | 例子 |
|---|---|---|---|
| **语义路由** | 会话模型打标记 | 时机依赖对话语义 | 该提示上传图片了；信息已够可生成；该问邮箱了 |
| **确定性路由** | 前端事件直接响应 | 用户物理操作，时机确定 | 点登录、复制链接、下载二维码、用户主动说"生成" |

两层都不需要独立的前置模型。独立前置模型只有在出现"时机既不确定、又不能等会话模型说完一整句"的需求（如输入时实时拦截分流）时才有意义——当前没有此类需求，明确不引入。

两条路径可以指向同一个组件：模型打 `UPLOAD` 标记唤起上传卡（语义路由），用户消息命中生成意图时前端直接浮出确认卡（确定性路由，现有 `publishIntent` 逻辑保留）。

## 三、协议规范

### 3.1 标记语法

```
[[ACTION:TYPE key=value key2=value2]]
```

- 位置：必须在回复**最末尾单独一行**；
- 数量：每条回复**至多一个**标记；多个时只取最后一个，其余按正文剥离；
- 参数：`key=value` 对，空格分隔；value 不含空格（需要空格的值用 `_` 连接或省略）；参数均为可选；
- 用户**永远不应看到**标记原文（剥离责任在后端，见 4.1）。

### 3.2 动作类型表（首批）

| TYPE | 浮现 UI | 可选参数 | 参数用途 |
|---|---|---|---|
| `UPLOAD` | 图片上传卡 | `slot`（hero/avatar/product/gallery）、`hint`（用途提示词） | 上传卡预填说明；`slot` 随图片存库，透传给生成模型 |
| `READY` | 生成确认卡 | `reason`（一句话总结为何已就绪） | 确认卡文案 |
| `PUBLISH` | 直接进入发布前确认/自动发布链路 | `reason` | 仅在用户当前轮明确授权生成时生效；前端还会做用户语义二次确认 |
| `EMAIL` | 邮箱绑定卡 | — | 发布后引导留邮箱（替代现在写死在 result 回调里的话术触发） |

扩展规则：新增动作 = 在此表加一行 + 前端加一个渲染分支 + prompt 加一条说明。不需要动协议本身。

### 3.3 裁决边界（安全模型）

标记是模型的**建议**，不是指令：

- `READY` 标记只浮出确认卡；真正生成仍由用户点击 + 后端额度/Turnstile 裁决（现有架构不变）；
- `PUBLISH` 标记必须同时满足“模型建议发布”和“用户当前消息包含明确生成/发布意图”，否则降级为确认卡；
- `UPLOAD` 标记只浮出上传卡；上传量限制仍由后端 per-session 上限管控；
- 模型乱打标记的最坏后果是多浮一张卡，不会产生越权动作。

## 四、改动点（三个文件）

### 4.1 `api/chat.php` — 标记提取泛化 + 流尾缓冲

**现状**：流式转发原样吐 delta，结束后用正则检测/剥离 `[READY]`，发 `sse_event('ready')`。

**改为**：

1. **流尾缓冲**：转发 delta 时维护一个尾部缓冲区（保留最近 ~64 字符不立即下发），确保 `[[ACTION:...]]` 不会拆包流到前端——这同时修复现有的 `[READY]` 闪烁问题。流结束时缓冲区若不含标记则补发；
2. **泛化提取**：

```php
// 流结束后
if (preg_match('/\[\[ACTION:([A-Z]+)((?:\s+\w+=\S+)*)\]\]\s*$/u', $assistant, $m)) {
    $action = $m[1];                       // UPLOAD | READY | PUBLISH | EMAIL
    $params = parse_action_params($m[2]);  // ['slot' => 'hero', ...]
    $clean  = preg_replace('/\s*\[\[ACTION:[^\]]*\]\]\s*$/u', '', $assistant);
    // 白名单校验：未知 TYPE 一律忽略（只剥离不转发）
    if (in_array($action, ['UPLOAD', 'READY', 'PUBLISH', 'EMAIL'], true)) {
        if ($action === 'READY') {
            db_exec('UPDATE sessions SET state=?, updated_at=? WHERE id=?', ['ready', now_iso(), $sessionId]);
        }
        sse_event('action', ['type' => strtolower($action), 'params' => $params]);
    }
}
```

3. **兼容**：保留旧 `[READY]` 检测一个过渡期（模型偶尔回退到旧格式时仍可用），映射为 `action: ready`；
4. SSE 事件 `ready` 退役，统一为 `action`。

### 4.2 `js/ai-app.js` — 动作分发 + 删除正则猜测

1. **删除** `maybeShowUploadCard` 及其正则（脆弱机制整体退役）；
2. **删除**前端逐 delta 剥离 `[READY]` 的代码（4.1 的流尾缓冲已保证标记不会到达前端）；
3. 新增 `action` 事件分发：

```js
action: function (d) {
  if (d.type === 'upload') addUploadCard(d.params);   // params.hint 预填说明输入框
  if (d.type === 'ready')  showGenerateCard(d.params.reason || '信息已经足够。');
  if (d.type === 'publish') handlePublishAction(d.params); // 仍需用户当前消息有生成语义
  if (d.type === 'email')  showEmailCard();           // 从 renderDelivery 中拆出复用
}
```

4. `addUploadCard(params)`：说明输入框 `value` 预填 `params.hint`（用户可改），`params.slot` 作为隐藏字段随上传提交；
5. 确定性路由保留：`publishIntent` 正则（用户主动说"生成/发布"）继续直接浮确认卡，不依赖模型标记。

### 4.3 `prompts/chat-system.txt` — 标记规则 + few-shot

替换现有第 5、6 条流程说明，新增协议段：

```
【动作标记】
当你的回复需要唤起界面组件时，在回复最末尾单独一行输出一个标记（用户看不到它）：
- 需要用户上传图片时：[[ACTION:UPLOAD slot=用途 hint=一句话说明]]
  slot 从 hero/avatar/product/gallery 中选
- 信息已足够生成页面时：[[ACTION:READY reason=一句话总结]]
- 其余情况不输出任何标记
规则：每条回复至多一个标记；标记必须是最后一行；不要向用户解释或提及标记。

【示例】
用户：活动是6月20日在杭州天目里，电话0571-88888888
你：信息很全！这个活动页放一张主视觉海报会更有气氛，有现成的图吗？
[[ACTION:UPLOAD slot=hero hint=活动主视觉海报]]

用户：没有图，直接做吧
你：好的，要点已齐：活动页 · 时间地点电话齐全 · 无配图。可以开始生成了。
[[ACTION:READY reason=核心信息已收集完整]]
```

### 4.4 数据库（小改）

`images` 表增加 `slot TEXT DEFAULT ''` 列；`api/upload.php` 接收并存储；`session_images_context()`（`includes/imageproc.php`）把 `slot` 一并输出到生成阶段的图片清单 JSON，让 sonnet 知道每张图的版位意图。

## 五、实施顺序与验收

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| 1 | chat.php 流尾缓冲 + `action` 事件 + 旧 `[READY]` 兼容 | 标记任何拆包方式下前端都看不到原文；`ready` 行为与现状等价 |
| 2 | chat-system.txt 协议 + few-shot；用 mock 与真实 gemma 各跑一遍 | 10 轮典型对话中标记出现位置与格式全部合规 |
| 3 | ai-app.js 动作分发，删除 `maybeShowUploadCard` 与前端剥离逻辑 | 上传卡仅在收到 `action:upload` 时出现且预填 hint；生成卡双路径（标记/用户意图）都工作；`PUBLISH` 必须通过用户语义二次确认 |
| 4 | images.slot 列 + 上传链路 + 生成清单透传 | 生成请求的图片清单 JSON 中可见 slot 字段 |
| 5 | EMAIL 动作接入发布后流程 | 发布成功后邮箱卡由 `action:email` 或前端确定性逻辑浮现，二选一兜底 |

回归点：编辑模式会话（seed 含大段 HTML）下标记协议同样生效；额度耗尽时 `notice` 事件与 `action` 事件互不干扰。

## 六、决策记录（合并进 V2-DESIGN.md 第十二部分）

| 决策 | 结论 | 理由摘要 |
|---|---|---|
| 是否引入独立前置路由模型 | **否** | 延迟叠加、成本倒挂、判断权错位；详见本文第一部分 |
| UI 唤起机制 | 会话模型内联动作标记 `[[ACTION:TYPE k=v]]` | 一次调用完成问答+路由；约束极强，gemma 量级可靠 |
| 路由分层 | 语义路由（模型标记）+ 确定性路由（前端事件），两层均无独立模型 | 用户物理操作不应经过任何模型 |
| 标记剥离责任 | 后端流尾缓冲，前端永不接触标记原文 | 顺带修复 `[READY]` 拆包闪烁 |
| 标记的权限性质 | 仅为建议；生成/上传的真实裁决在后端额度与 Turnstile | 模型乱打标记最坏只是多浮一张卡 |
| PUBLISH 自动生成门槛 | 模型 `PUBLISH` + 用户当前轮明确生成语义 | 解决“光说不练”，同时避免模型单方面烧额度 |
| 重新引入前置模型的条件 | 出现"不能等会话模型说完整句"的实时拦截分流需求时再评估 | 当前无此需求 |
