## 二、上线阻断问题

### P0-1：生产 Nginx 直接公开后台 partial PHP 源码

生产配置 `/www/server/panel/vhost/nginx/xlog.ink.conf:57-60` 使用：

```nginx
location ^~ /partials/ {
    try_files $uri =404;
}
```

`^~` 阻止请求继续进入 PHP 正则处理器，因此 `.php` 文件被作为静态文件下载。实测：

```text
GET https://xlog.ink/partials/admin/users.php
HTTP 200
Content-Type: application/octet-stream
Content-Length: 3441
Body: <?php ...
```

当前 `partials/admin/*.php` 全部位于公开 webroot，生产权限为 `0644`。代码中没有浏览器端对 `/partials/` 的依赖，后台仅通过 PHP `require` 使用这些文件。

必须：

1. 删除公开 `/partials/` 放行规则；
2. 至少增加 `location ^~ /partials/admin/ { return 404; }`；
3. 如旧页面仍依赖 `partials/footer*.html`，只精确放行所需 `.html` 文件，禁止整个目录；
4. 上线验证所有 `partials/admin/*.php` 返回 404。

### P0-2：主站与通配符子域仍共用一个 server，严格 CSP 未部署

生产配置仍为：

```nginx
server_name xlog.ink *.xlog.ink;
```

这与 [nginx-v2-snippet.conf](./nginx-v2-snippet.conf) 要求的主站/生成页分离不一致。实测：

- `https://pagefye.xlog.ink/api/auth/me.php` 返回主站 API JSON；
- 生成页响应没有 Nginx `Content-Security-Policy`；
- 生产共有 2261 个历史 HTML，其中 2193 个同时包含 `<script>` 且没有 CSP meta；
- 抽样历史页面包含外部 CDN 脚本、内联脚本、外部图片和加密货币推广链接。

新发布链路会清理模型脚本并注入 CSP meta，但无法保护历史页面，也不能替代响应头隔离。

必须：

1. 按文档拆成 apex 主站 server 与 wildcard 生成页 server；
2. wildcard 仅允许 `/` 映射页面及必要的静态资源，不允许访问 `/api`、`/admin.php`、源码目录；
3. wildcard 响应统一发送 `script-src 'none'` 的 CSP；
4. 对历史页面批量加 CSP 响应头，不依赖逐文件重写；
5. 执行 `scripts/audit-page-risk.php`，处理风险页面后保留 CSV 报告。

### P0-3：HTTP 未强制跳转 HTTPS，源站仍启用 TLS 1.1

证书本身正常：

- SAN：`xlog.ink`、`*.xlog.ink`
- 颁发者：Let's Encrypt
- 有效期：2026-07-26 至 2026-10-24

但实测 `http://xlog.ink/` 返回 200，而非 301/308。首次使用 HTTP 的用户会获得非 Secure 会话/cookie，登录和后台入口存在降级传输风险。生产 Nginx 还配置了 `ssl_protocols TLSv1.1 TLSv1.2 TLSv1.3`。

必须：

1. Cloudflare 开启 Always Use HTTPS；
2. 源站 80 端口独立 server，除 ACME 外全部 301 到 HTTPS；
3. 删除 TLS 1.1，仅保留 TLS 1.2/1.3；
4. HSTS 建议增加 `includeSubDomains`，确认所有子域均支持 HTTPS 后再启用。

## 三、高优先级问题

### P1-1：普通发布存在 slug TOCTOU，可覆盖其他用户页面

[content_tools.php](../includes/content_tools.php) 的 `generate_semantic_slug()` 先用 `slug_exists()` 检查可用性；[publish.php](../api/publish.php) 随后先写 `/site/{slug}.html`，再查询 `pages`：

```php
file_put_contents($path, $html, LOCK_EX);
if (db_one('SELECT slug FROM pages WHERE slug = ?', [$pageSlug])) {
    db_exec('UPDATE pages SET ... WHERE slug = ?', ...);
}
```

两个会话并发请求同一自定义前缀时，都可能通过“可用”检查。后到者会覆盖文件，并在发现数据库已有 slug 后走 `UPDATE`，即使它不是编辑会话。结果是跨用户页面覆盖。

修复要求：

- 普通创建只允许 `INSERT`，绝不能因 slug 已存在而转为 `UPDATE`；
- 在事务中原子预留 slug，依赖主键唯一约束冲突后重新生成后缀；
- HTML 先写临时文件，数据库记录成功后原子 rename；
- 只有已验证的 `$editPage` 才允许 UPDATE 原 slug。

### P1-2：Turnstile 在生产关闭

生产诊断明确显示 `Turnstile config - disabled`。虽然已有 IP/cookie 额度、会话创建和上传限额，但自动化攻击仍能更换出口/IP 放大 AI 成本。历史计划要求生产发布前必须通过 Turnstile。

必须在生产配置真实 site/secret key，并回归：

- 无 token 发布失败且不扣额度；
- 无效 token 不进入模型；
- 有效 token 正常发布；
- Cloudflare 代理下 `client_ip()` 仍为真实访客 IP。

### P1-3：61 个目标模式文件仅暂存，GitHub 主线仍是旧版本

本地和生产核心文件 SHA-256 一致，但：

```text
local HEAD:  e9eb8aec60556033885bd62a85fdaa34be83379a
GitHub main: e9eb8aec60556033885bd62a85fdaa34be83379a
staged files: 61
```

支付、后台、HTML 清理、额度、访客体系和新测试均未进入提交。当前生产状态无法从 GitHub 恢复，回滚或换机时会丢失全部目标模式改动。

必须先修复本审计 P0/P1 代码项，再形成一个可复现提交，跑完整验收后推送 GitHub。

### P1-4：历史页面风险扫描脚本已实现，但生产未执行

`scripts/audit-page-risk.php` 已存在，生产 `data/reports/` 没有报告。当前 2261 个历史页面中，抽样已经看到加密货币推广及外部脚本内容。

上线动作：

- 在只读/报告模式先跑全量扫描；
- CSV 至少记录 slug、风险分类、成人门状态、证据摘要、复核状态；
- 高风险页面先下线或隔离，再人工复核；
- 扫描失败不得自动删除页面。

## 四、中优先级问题

### P2-1：停用用户仍可登录并保持有效身份

[verify.php](../api/auth/verify.php) 按邮箱读取用户后不检查 `status`，直接写入 `$_SESSION['user_id']`；[bootstrap.php](../includes/bootstrap.php) 的 `current_user_id()` 也只读取 session；[me.php](../api/auth/me.php) 和 [my-pages.php](../api/my-pages.php) 查询时同样不限制 active。

额度模块会过滤 `status='active'`，因此停用用户会表现为“能登录、能看页面，但额度异常”，而不是被一致拒绝。

建议：

- 验证码登录只允许 active 用户；
- `current_user_id()` 或统一 `current_user()` 在每次敏感请求校验状态；
- 停用后清除现有 session 的策略应有明确实现；
- 增加 suspended/disabled 用户回归测试。

### P2-2：支付渠道密钥仍明文保存在 webroot 下的 SQLite

[db.php](../includes/db.php) 的 `pay_channels` 保存 `md5_key`、商户私钥、平台公钥；[pay.php](../includes/pay.php) 的后台保存逻辑直接写入数据库。虽然 `/data` 已由 Nginx 屏蔽、数据库权限为 `0660`，但数据库备份、PHP 文件读取漏洞或运维导出会同时暴露订单和支付密钥。

建议将密钥改为：

- 数据库只存 `secret_ref`；
- 真实值放 `/etc/xlog/config.php`、环境变量或专用 secret 文件；
- 若必须入库，使用位于 webroot 外的主密钥进行应用层加密，并提供轮换方案。

### P2-3：`schema_migrations` 只是空壳，仍无版本迁移与外键

[db.php](../includes/db.php) 创建了 `schema_migrations`，但全项目没有写入或读取该表；实际升级仍依赖 `db_ensure_column()`。所有业务表的 `PRAGMA foreign_key_list` 都为空，`PRAGMA foreign_keys=ON` 没有实际约束。

风险包括孤儿 session/images/orders/transactions、部署中途失败无法判断版本，以及多实例升级顺序不确定。

建议从当前结构建立 baseline migration，后续使用单调版本迁移，并为可安全约束的关系补外键或显式清理策略。

### P2-4：HTML “allowlist sanitizer” 实际仍是正则 denylist

[html_sanitize.php](../includes/html_sanitize.php) 能清除 `<script>`、事件属性、iframe/form 和常见 `javascript:`，这是明显改善；但实测以下内容仍通过断言：

- 未加引号的外站 `<img src=https://evil.example/...>`；
- 外站 `srcset`；
- `<style>@import url(https://evil.example/...)`。

新页面的 CSP meta 会阻断这些资源，但安全依赖 CSP 正确注入和浏览器执行。生产 wildcard 响应头缺失时，历史页面没有第二层防线。

建议使用 DOM 解析器做元素/属性/协议 allowlist，并独立校验 `srcset` 与 CSS URL；Nginx CSP 仍保留为第二层。

## 五、低优先级与工程卫生

### P3-1：动态审计脚本仍绑定开发机绝对路径

`scripts/codex-dynamic-audit.js` 写死：

```js
const RUNTIME_NODE_MODULES =
  '/Users/apple/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules';
```

换机或 CI 无法直接运行。应改为环境变量/依赖探测，并在缺依赖时给出安装说明。

### P3-2：核心文件体积继续增长

- `js/ai-app.js`：1797 行
- `css/page-ai.css`：1683 行
- `includes/pay.php`：917 行
- `includes/i18n.php`：786 行
- `includes/ai.php`：754 行

目前功能仍可运行，但后续修改容易形成跨模块回归。建议按动作卡、账户抽屉、交付卡、支付驱动、模型协议拆分，不做无测试保障的大重构。

### P3-3：测试输出已干净，但缺少真实 php-fpm 并发回归

六组 PHP 回归脚本全部 exit 0，当前无 warning。内置 `php -S` 单线程无法验证：

- 同 slug 并发发布；
- 同 session 双 publish；
- SQLite busy/retry；
- 支付回调与主动查询同时到账。

应在 staging php-fpm 上增加并发验收。

### P3-4：当前暂存集未通过 `git diff --cached --check`

多份新规划文档使用行尾双空格作为 Markdown 换行，`git diff --cached --check` 会报告大量 trailing whitespace；`AUDIT-7-2026-07-26.md` 还报告 EOF 多余空行。它不影响运行，但会阻断启用了 whitespace check 的 CI/合并流程。提交前应统一 Markdown 格式约定并清理。
