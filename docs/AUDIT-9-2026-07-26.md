## 二、高优先级问题

### P1-1：发布的数据库记录、HTML 文件和资源目录尚未形成一致提交

涉及：

- `api/publish.php:157-247`
- `includes/content_tools.php:366-380`
- `includes/content_tools.php:426-482`
- `includes/imageproc.php:230-264`

#### 创建页面

普通创建流程先生成一个 provisional slug，并立即把上传资源从临时目录移动到该 slug：

```php
$provisional = generate_semantic_slug(...);
$html = move_session_assets_to_slug($sessionId, $provisional['slug'], $html);
```

随后 `publish_insert_new_page()` 会再次调用 `generate_semantic_slug()`，预留真正写入数据库的 slug。自动 slug 每次都带随机后缀，因此两次结果通常不同，并非注释所说的“rare”。

后果：

1. 图片文件和 `images.slug` 可能停留在 provisional slug，而页面记录使用另一 slug；
2. HTML 会再次注入 footer，形成重复访问像素；
3. 成人页会再次注入 adult gate；
4. 后续按页面 slug 清理或迁移资源时，页面与资源归属不一致。

此外，创建流程先插入 `pages.status='live'`，再写 HTML。若磁盘满、权限错误或 rename 失败，异常处理只退款和恢复 session，不删除已插入的 live 记录。后台、recent 和 sitemap 可能出现指向不存在文件的页面。

#### 编辑页面

编辑流程顺序相反：先替换线上 HTML，再更新数据库。若数据库更新失败，用户会收到“生成失败”和退款，但页面文件已经发生变化，数据库元数据和会话状态仍是旧值。

#### 修复要求

1. 创建流程先原子预留最终 slug，状态设为 `pending`；
2. 只在最终 slug 确定后移动资源、写 meta、adult gate、footer 和访问像素；
3. HTML 成功落盘后再把页面切换为 `live`；
4. 创建失败必须删除 pending 行，并清理或回迁本次移动的资源；
5. 编辑流程使用临时文件和原文件备份，数据库或 rename 任一步失败时执行补偿回滚；
6. 注入函数应具备幂等标记，避免重复 adult gate 和访问像素；
7. 增加“最终 slug 与 provisional 不同”“文件写失败”“数据库更新失败”三组回归测试。

### P1-2：生产 Nginx 仍会公开内部文档和部署材料

涉及 `docs/nginx-xlog.ink.prod.conf:59-90`。

当前主域只屏蔽：

```nginx
location ~ ^/(?:data|includes|prompts|scripts)(?:/|$) { return 404; }
location ^~ /partials/ { return 404; }
```

但仓库还包含 80 余个 webroot 内部文件，包括：

- `docs/AUDIT-*.md`
- `docs/*NEXT-DEV.md`
- `docs/*.conf`
- `migrations/*.php`
- `deploy.example.env`

主域 `location /` 会优先提供存在的静态文件。部署整个仓库后，审计报告、架构、已知缺陷、运维配置和设计草稿可能被直接下载。`migrations/*.php` 即使当前由 PHP 执行为空响应，也不应成为公开入口。

#### 修复要求

建议主域至少增加：

```nginx
location ~ ^/(?:data|includes|prompts|scripts|docs|migrations|partials)(?:/|$) {
    return 404;
}

location = /deploy.example.env {
    return 404;
}
```

同时将部署改为 allowlist 制品，优先只同步运行所需文件，而不是把完整 Git 工作区作为 webroot。

验收必须覆盖 `/docs/`、`/migrations/`、`/deploy.example.env`、`/data/`、`/includes/`、`/prompts/`、`/scripts/` 全部返回 404。

## 三、中优先级问题

### P2-1：支付 `secret_ref` 只完成了运行时读取，后台保存链路未闭环

涉及：

- `includes/pay.php:103-139`
- `includes/pay.php:266-337`
- `admin.php:59-83`
- `partials/admin/channels.php:84-116`

`pay_channel_hydrate_secrets()` 已能从外部配置加载 `secret_ref`，但后台表单没有 `secret_ref` 字段，`pay_channel_save()` 也不保存它。编辑已有外部密钥渠道时，保存逻辑仍直接读取数据库中的明文密钥列并检查完整性。

结果是：

- 外部密钥渠道可运行，但不能通过后台完整创建和维护；
- SQLite 明文密钥仍是默认路径；
- 测试只覆盖了 `secret_ref=''` 的 passthrough，没有验证真实外部引用。

建议让后台只管理 `secret_ref` 和非敏感配置，密钥输入仅保留为明确的兼容模式，并补充外部密钥缺失、轮换、编辑和回调验签测试。

### P2-2：版本迁移没有事务边界

`includes/db.php:226-253` 会先执行 migration 的 `up()`，再写入 `schema_migrations`，中间没有事务。

未来一个 migration 包含多条语句时，如果执行到一半失败，会留下部分结构变更且没有版本标记。重启后再次执行是否安全完全依赖每个 migration 自行实现幂等。

建议每个 migration 使用独立事务：

1. `BEGIN IMMEDIATE`；
2. 执行 `up()`；
3. 写入版本；
4. `COMMIT`；
5. 异常时 `ROLLBACK` 并终止启动。

对于 SQLite 不支持事务化的特殊 DDL，应由 migration 显式声明并提供恢复检查。

## 四、低优先级与工程卫生

现有 `scripts/test-publish-slug.php` 验证了 INSERT-only 和 slug 唯一性，但没有覆盖：

这些正是 P1-1 的风险来源，应在修复时作为验收门槛。

### P3-2：测试脚本仍有 session/header 警告噪音

完整回归均返回成功，但以下脚本会因输出发生在 `session_start()` 前产生 warning：

- `scripts/test-audit7-hardening.php`
- `scripts/test-user-status.php`
- `scripts/test-guest-user-flow.php`

建议测试入口先启动输出缓冲或把标题输出放到 session 初始化之后，避免 CI 将真实 warning 淹没。

### P3-3：历史文档和无调用安全策略仍有漂移

`includes/helpers.php:154-167` 还保留一套允许内联脚本和外部统计脚本的旧 generated-page CSP。当前发布链路未调用它，但与 `includes/html_sanitize.php` 的严格策略并存，容易在未来复用时恢复旧边界。建议删除未调用的旧生成页 helper，或明确改名为 legacy 并加入禁止调用测试。
